# CodeCanvas · 一句话生成应用

用一句自然语言描述需求，AI 自动完成需求澄清、任务规划、代码生成、质量校验与自检修复，
结果实时预览在沙箱里，可以继续用对话迭代，随时回滚到任意版本，**一键发布成公开链接给别人用**。

后端 Java 17（编译目标）/ 运行在 JDK 21、Spring Boot 3.5、LangChain4j + 自研 Agent 编排；前端 React 18 + TypeScript + Vite。

> **为什么编译目标是 17、运行用 21**：`--release 17` 让同一个 jar 在 17 和 21 上都能跑，
> 而 Agent 线程池会在 21+ 自动切换成虚拟线程（反射探测，见 `CodeCanvasConfig`）。
> 少一道"必须升 JDK"的部署门槛，同时在 21 上拿到虚拟线程的收益 ——
> 有对照实验：`backend/tools/VirtualThreadBench.java`。

**线上体验**：http://114.215.186.113/canvas/ （免密，每 IP 限流 10 次/分钟）

## 发布与分享

点顶栏「发布」，后端生成一个 8 位部署密钥，弹出形如
`http://<host>/canvas/a/wq69fdrp` 的链接——**任何人打开这个链接看到的就是应用本身**，
没有平台外壳、不需要登录。这正是"做出来的东西能被别人看到"的那一步。

三个刻意的设计：

- **密钥幂等**：重复发布沿用第一次的密钥。密钥一变，之前发给面试官/朋友的链接就全废了
- **发布内容永远跟随当前版本**：改了需求再点发布，链接不变、内容更新，不需要重新分享
- **后端只返回密钥，不返回完整 URL**：后端并不知道自己被部署在哪个域名或子路径下，
  硬拼地址在换域名、加 HTTPS、改前缀时都会失效；由前端用当前访问地址推导出来才永远正确

**给发布的应用套了一层 CSP**：`connect-src 'none'` 挡掉生成应用的 fetch/XHR。
否则一个"手滑写坏的"应用可以循环调用平台的生成接口，把模型额度刷光。
`default-src` 同时限制为本地与内联资源，与提示词里"不引用任何外部资源"的约束正好一致。

## 一分钟跑起来

**后端**（需要 JDK 17+，Maven 3.9+）

```bash
cd backend
./run.sh                 # 会加载 .env 里的模型配置
```

服务起在 `http://localhost:8080`。没有模型密钥也能跑——会自动使用内置的离线演示引擎，
整条链路（流式输出、静态校验、自检修复、版本快照）都会被真实执行一遍。

**接真实模型**

把密钥和模型写进 `backend/.env`（该文件已在 `.gitignore` 中，不会进仓库）：

```bash
CODECANVAS_PROVIDER=openai
CODECANVAS_OPENAI_BASE=https://dashscope.aliyuncs.com/compatible-mode/v1   # 阿里云百炼
CODECANVAS_OPENAI_KEY=sk-xxxxxx
CODECANVAS_MODEL_FLAGSHIP=qwen3-coder-next
CODECANVAS_MODEL_STANDARD=qwen3-coder-plus
CODECANVAS_MODEL_LIGHT=qwen3-coder-flash
```

换厂商只改两处：`BASE` 指向 DeepSeek / GLM / 硅基流动等任意 OpenAI 兼容端点；
把 `PROVIDER` 改成 `anthropic` 则切到 Claude 协议（此时填 `CODECANVAS_ANTHROPIC_*`）。

> ⚠️ `pricing` 里的单价是**占位估算值**，成本看板据此计算。
> 对外引用成本数字之前，请先照搬厂商价目表把它换成真实价格。

**前端**

```bash
cd frontend
npm install
npm run dev
```

打开 `http://localhost:5173`，输入「做一个记账小工具」试试。

## 部署

线上地址：**http://114.215.186.113/canvas/**（直接可访问，未设访问口令）

```bash
cd deploy
SSH_PASS='服务器密码' ./deploy.sh     # 首次：构建 → 上传 → 服务器端安装，并装上公钥
./deploy.sh                           # 之后：免密部署
ENABLE_AUTH=1 ./deploy.sh             # 需要访问口令时加这个开关
RATE_LIMIT=off ./deploy.sh            # 关闭限流（默认开启）
```

| 文件 | 作用 |
|------|------|
| `deploy.sh` | 本地一键：构建前端 + 后端 fat jar → 上传 → 触发远程安装 |
| `remote-setup.sh` | 服务器端幂等安装：JDK 21（装不上退回 17）→ systemd 服务 → nginx location → 限流 →（可选）访问口令 |

**部署形态**：沿用服务器上已有的「一个 80 端口站点 + 多项目路径前缀」惯例，
CodeCanvas 挂在 `/canvas/` 下，与 `/mira/`、`/jobagent/` 平级。**不新建站点、不动端口、不碰其他项目。**

几个必须这么做的点：

- **后端只监听 `127.0.0.1:18080`**。公网不可直连，流量统一过 nginx——限流与鉴权都在这一层
- **`proxy_buffering off`**。不关的话生成过程的 SSE 增量会被 nginx 攒着一起发，前端看不到逐字输出
- **注入 nginx 配置前先备份**，且只往站点里加一行 `include`；全部自定义配置单独放在
  `/etc/nginx/codecanvas-locations.conf`，卸载就是删文件 + 删那行
- **内存给紧一点**：机器只有 1.7G 且无 swap，堆设为 `-Xmx448m` 并启用 `UseSerialGC`

**限流**：默认每个 IP **10 次/分钟、突发 6 次**，超出返回 429。
一次真实生成要 20~40 秒，正常使用碰不到这个上限——它的作用是挡爬虫和恶意刷模型额度。
`limit_req_zone` 只能写在 http 上下文，所以单独放在 `conf.d/codecanvas-ratelimit.conf`，
location 里只做引用。实测：连发 14 次，6 次通过（突发额度）、8 次被拒。

**访问口令默认关闭**，任何人可直接访问并消耗模型额度——这是刻意的取舍，方便演示和分享。
要开启用 `ENABLE_AUTH=1 ./deploy.sh`。开启时有个必须注意的坑：
口令文件的属主**必须是 `root:www-data`**，只给 640 权限但属主是 root 时 nginx worker 读不到，
表现是「不带口令返回 401 正常、带上正确口令反而 500」（实际踩过一次）。

**前端子路径部署**：生产构建前缀由 `frontend/.env.production` 的 `CODECANVAS_BASE` 控制，
API 前缀由 Vite 的 `BASE_URL` 推导（见 `src/api/client.ts`），所以同一份代码既能跑在开发环境根路径，
也能部署到 `/canvas/` 而不需要改代码。

**回滚**：删除 `/etc/nginx/codecanvas-locations.conf`，从 `/etc/nginx/sites-available/crossborder`
移除 include 行，再 `systemctl disable --now codecanvas`。

## 模型怎么选的（有实测依据）

选型不是看榜单，而是拿同一个"生成一个完整番茄钟页面"的请求实测出来的：

| 模型 | 耗时（3 轮均值） | 单次生成量 | 结论 |
|------|------|-----------|------|
| `qwen3-coder-next` | **13.3s** | **13899 字符** | **旗舰档**，更快且产出翻倍 |
| `qwen3-coder-plus` | 14.3s | 6773 字符 | 标准档 |
| `qwen3-coder-flash` | 秒级 | 小 | 轻量档 |
| `qwen3-max` | 18s | 62 KB 流 | 无思维链的通用模型，旗舰档备选 |
| `qwen3.8-max` | **243s** | 788 KB 流 | 带思维链，reasoning 流把耗时放大 20 倍 |

**怎么测才有意义**：最早我用"短提示词 + `max_tokens=4000`"对比，得出"coder-plus 更快"——
那是错的：两个模型都提前撞到输出上限，比的其实是谁先生成完 4000 token，而不是谁能在同样时间里
产出更多可用代码。换成平台真实的完整提示词、放开输出长度后重测 3 轮，结论正好反过来：
**coder-next 用更少的时间产出了多一倍的代码**。教训是——**对比模型必须用真实提示词和真实输出长度，
否则测的是你自己的参数，不是模型的能力。**

**切换模型时的两个约束**：
1. 同一个模型出现在多个档位时，各档位单价必须一致（`pricing` 配置），否则同一笔调用会被算出两个成本
2. 带思维链的模型（`qwen3.8-max` 等）不能放在生成主链路上，`reasoning_content` 的流式输出
   会把耗时放大 20 倍

`qwen3.8-max` 是更强的通用模型，但在这个场景里是**错误选择**：它把大量 token 花在思维链上，
用户要等 4 分钟。一条实用结论是——**生成主链路上的模型要"够好且够快"，而不是"最强"**。

这也引出另一个设计：整体超时能兜住"生成内容很长"，但兜不住"模型卡死了"。
所以网关另外做了 **首字节超时**（默认 45 秒）：流式调用超过这个时间还没有任何内容返回，
就判定该候选不可用、立刻降级。没有这一层，一个卡住的主模型会让用户白等满整个超时
（这个坑是实测踩到的，当时一次生成耗了 5 分 3 秒，最后还降级到了离线引擎）。

## 五个阶段

```
需求澄清 → 任务规划 → 代码生成 → 质量校验 → 自检修复
```

每个阶段都是显式状态机里的一步，可在界面上看到进度，出问题能直接定位到阶段，
而不是面对一条看不见的回调链。

| 阶段 | 做什么 | 怎么算完成 |
|------|--------|-----------|
| 需求澄清 | 把一句话需求固化成结构化 PRD，多轮迭代时不再重复澄清 | PRD 落库，后续每轮复用 |
| 任务规划 | 判断本轮任务类型、挑选相关文件、决定模型档位 | 产出可解释的路由理由 |
| 代码生成 | 流式产出页面代码，通过工具写盘 | 文件写入工作区 |
| 质量校验 | 静态检查标签闭合、脚本括号配平、占位符残留 | 问题清单为空 |
| 自检修复 | 把问题清单回注给模型定点修复，最多 3 次 | 校验通过，或达到重试上限 |

## 四个核心设计

### 1. 自检修复闭环

**问题**：模型生成的代码"看起来对"但经常跑不起来，用户拿到的是打不开的页面。

**方案**：结果必须先过静态校验才有资格交付。校验器做的是确定性检查（不依赖模型）：
HTML 骨架完整性、标签闭合顺序、script 内括号配平（会先剔除字符串与注释，避免误判）、
占位符残留。不通过就把具体问题当作错误信息回注，要求模型做最小必要修改。

**还有一条更真实的路径**：预览使用独立源的沙箱 iframe，浏览器会拒绝页面内访问 localStorage
并抛 `SecurityError`。平台在预览页最前面注入了错误探针，通过 `postMessage` 把运行时异常回传，
自动触发一次定点修复——「生成的页面报错了」从用户投诉变成了系统能力。

### 2. 上下文工程

**问题**：多轮迭代如果把历史对话和全部历史代码原样塞进提示词，成本随轮次线性上涨，
模型被无关内容干扰开始忘事，最后直接超出上下文窗口。

**方案**：
- 首轮把需求固化成结构化 PRD，之后每轮注入 PRD + 历史变更摘要，而不是原始对话流
- 按需求文本与文件内容的匹配度打分，只注入相关文件（单文件时退化为它自己，多文件时开始起作用）
- 给注入内容设 token 预算，超预算就截掉长文件的中段并明确标注，而不是让请求直接失败

**盈亏平衡点要说清楚**：结构化 PRD 是一笔约 200 token 的固定开销，前两轮还没有足够历史
可以摊薄它，此时注入量反而**高于**"全量历史"的估算值（界面上会如实显示成负数）。
从第三轮左右开始转为净收益，轮次越多收益越大。本项目刻意不对这个百分比做非负截断——
报一个好看的假数字，在面试官追问"第几轮开始省"的时候就崩了。

### 3. 多轮迭代的意图判断（重建 vs 打补丁）

**问题**：用户在一个已有项目里又说了一句"做一个番茄钟"。如果按增量修改处理，
模型会在记账页面上加一个番茄钟模块，出来的东西谁都不满意。

**方案**：识别"重新描述整个应用"的语义（以「做一个 / 写一个 / 设计一个」开头，且项目已有内容），
判定为**重建**：重新抽取 PRD、按完整生成处理、覆盖当前文件，并明确告诉用户
「你在重新描述整个应用，本轮按重建处理，而不是在旧页面上打补丁」。
重建同样产生新版本快照，所以改错了还能退回去。

一条经验：**多轮 AI 应用里，"用户现在到底要什么"比"怎么改代码"更容易出错**。
不做这层判断，前面所有的上下文工程都白费。

### 4. 模型分级路由

**问题**：所有请求打同一个模型，要么贵（全用旗舰），要么差（全用轻量）。

**方案**：按任务类型、需求体量、关键词信号、是否首轮做复杂度打分，映射到旗舰 / 标准 / 轻量三档。
每次决策都带一份可读的理由（例如"涉及架构关键词 2 处(+2)，总分 7 → 标准档"），
配合 token 与成本计量，路由策略的收益是可观测、可回测的。

失败时按档位逐级降级（旗舰 → 标准 → 轻量），真实模型全部不可用时退回离线引擎。

**一个明确的边界**：流式输出一旦已有内容发给用户就不再重试——重试会让前端收到两份拼接的代码，
比直接报错更糟。

**怎么证明它真的省了钱**：只报"我做了分级路由"没有说服力，所以每次调用除了记实际花费，
还会按**旗舰档单价对同一批 token 再算一笔**（反事实基准）。两条曲线相减，就是路由省下的钱。

```
实际 ¥0.044570  /  若全走旗舰 ¥0.092856  /  省 52.0%
```

这个数字有三条自我约束，都写在 `TokenMeter` 的注释里、也一起返回给调用方：

- **把假设摊开**：`assumption` 字段随数字一起返回，界面上也显示。比例取决于各档位单价之比，
  而单价来自 `llm.pricing` 配置
- **把原料摊开**：`pricing` 与各档位的 token 量一起返回，别人可以拿自己的价目表重算
- **不编数**：基准为 0（没有调用、或全走离线引擎）时返回 0，不做"看起来好看"的兜底

顺带说明这个对照回答的是什么问题：**它回答"假设质量不掉的前提下省了多少"，
不回答"换档会不会变差"**——同样的 token 走不同档位，产出本来就不一样。

`GET /api/usage` 直接可查：

```bash
curl -s http://114.215.186.113/canvas/api/usage
```

### 5. 沙箱隔离

预览 iframe 使用 `sandbox="allow-scripts"` 且**不给** `allow-same-origin`，
浏览器按 opaque origin 处理，生成的脚本拿不到平台页面的 DOM、Cookie 和本地存储。

**刻意没做的事**：没有引入容器。当前生成物是单文件页面、无需安装依赖、无需构建，
iframe 隔离已经解决全部问题，上容器是过度设计。容器级隔离在 `DockerSandboxExecutor` 里预留了位置
并在接口上如实标注为「未启用 + 启用条件」，等到需要装依赖、跑构建或对外开放执行陌生代码时再实现。

## 技术选型与取舍

| 选择 | 理由 | 没有它会怎样 |
|------|------|-------------|
| Spring Boot 3 + Java 17 | 基础底座 | — |
| LangChain4j | 统一 OpenAI 兼容与 Anthropic 两种协议，换厂商只改配置 | 每换一个厂商就要改一遍业务代码 |
| 自研状态机编排（约 200 行） | 五阶段流程清晰、可观测、可单测 | 用 LangGraph4j 之类会多一层不透明的框架 |
| Redisson / Redis | **未引入**：当前是单实例、无并发限额需求，加进来只是增加部署负担 | 无 |
| MySQL | **未引入**：仓储层已抽象（`ProjectRepository`），换实现即可 | 无 |
| 文件系统持久化 | 零依赖、随时可跑、数据结构可直接查看 | — |
| Agent 线程池 | 优先虚拟线程（JDK 21+，反射探测），JDK 17 自动退回有界线程池。**线上跑 21，虚拟线程已启用** | 阻塞 IO 占满 Web 请求线程 |

判断标准只有一条：**这个组件能不能对应一个真实用户可感知的问题**。对应不上就不加。

## 接口

### `POST /api/chat/stream`（SSE）

请求：

```json
{
  "projectId": "p_ab12cd",
  "message": "做一个记账小工具",
  "trigger": "USER",
  "errors": null
}
```

`trigger` 为 `RUNTIME_ERROR` 时表示由前端捕获的运行时错误触发的自动修复，`errors` 携带错误详情。

事件流：

| 事件 | 载荷 | 说明 |
|------|------|------|
| `session` | `{projectId, created}` | 会话建立 |
| `stage` | `{stage, label, index, total, detail}` | 阶段推进 |
| `status` | `{text}` | 当前正在做什么 |
| `tool` | `{tool, args, result}` | 工具调用留痕 |
| `file` | `{path, action, bytes}` | 文件变更 |
| `delta` | `{path, text}` | 代码增量，前端累加 |
| `tokens` | 用量与路由信息 | 含上下文压缩比 |
| `heal` | `{attempt, reason, detail}` | 触发自检修复 |
| `result` | 完整结果 | 含 `previewHtml` 与工具轨迹 |
| `error` | `{message}` | 失败 |
| `done` | `{ok}` | 收尾 |

### 其他

- `GET /api/projects` — 项目列表
- `GET /api/projects/{id}` — 项目详情（含文件、版本、预览 HTML）
- `POST /api/projects/{id}/versions/{versionId}/activate` — 版本回滚
- `POST /api/projects/{id}/rename` — 重命名
- `GET /api/config` — 平台自述：模型模式、沙箱级别、线程模型、存储位置
- `GET /api/usage` — 成本台账：实际 / 反事实 / 差额 / 档位分布 / 所用单价 / 假设说明

## 虚拟线程：对照实验

`backend/tools/VirtualThreadBench.java` 是一个单文件可执行工具，不需要编译：

```bash
$JAVA_HOME/bin/java backend/tools/VirtualThreadBench.java 400 60   # 400 个任务，每个阻塞 60ms
```

它把变量隔离出来——两组执行**完全相同**的阻塞任务，唯一差别是调度它们的执行器。
用 `Thread.sleep` 而不是真调模型，是为了可复现且不花钱；
真实模型调用动辄等待数秒，虚拟线程的优势只会更明显。

实测（同一台机器，400 个任务 × 60ms 阻塞，有界池大小 16）：

| 执行器 | 墙钟 | 平台线程峰值 | 实际并发度 |
|--------|------|-------------|-----------|
| **虚拟线程（JDK 21）** | **84 ms** | 33 | **286 / 400** |
| 有界平台线程池（JDK 21） | 1554 ms | 16 | 15.4 / 400 |
| 有界平台线程池（JDK 17） | 1550 ms | 16 | 15.5 / 400 |

**同一批任务，虚拟线程快 18.5 倍**；承载 12 倍的并发度只用了 2 倍的平台线程。
有界池的并发上限就是池大小（16），超出的任务只能排队——这正是"阻塞 IO 场景"的典型瓶颈。

线上实际生效的线程模型可以直接查：`GET /api/config` 的 `executor` 字段会返回
`虚拟线程（Java 21.0.12）`，带上真实版本号，不用猜。

## 已知边界

- 生成物为**单文件 HTML 应用**，暂不支持多文件项目与依赖安装（那一步需要引入容器沙箱）
- 离线引擎能产出可交互页面并支持一批常见修改指令，复杂需求需要接真实模型
- 数据存在本地 `codecanvas-data/`，没有多用户隔离
- 版本快照按全文存储，文件多时应改为增量 diff
- 版本卡片上的"自检修复 N 次"统计的是**静态校验**触发的重试次数；
  运行时错误触发的修复走的是另一条路径，目前没有单独计数（界面文案上容易混淆，待补）
- 生产构建产物已生成在 `frontend/dist-verify/`（本机脚本对 `dist/` 的清理阶段被环境的
  安全删除机制拦截，用别的输出目录验证通过），可以删掉
